# 任务附带信息（notes）

日程条目除了「做什么、什么时候」，经常还带一份只在执行时才有用的细节：复现步骤、参数、公式、参考链接、验收标准、带什么材料。这些内容属于任务本身，不该挤进标题，也不该在日程过期后消失。

DayLeaf 用事件已有的 `notes` 字段保存这类信息。脚本一直是支持的；本文件说明 Agent 在什么情况下该写、怎么写，以及为什么卡片不显示它。

## 什么时候写入

- **写了操作细节 → 存入 `notes`。** 用户在同一句话里给出任务的执行信息（步骤、参数、公式、链接、目标、验收标准、复现要点、携带物品等），Agent 把这份信息结构化写入该事件的 `notes`，用换行分条，必要时加序号。
- **只有标题和时间 → 不写。** 省略 `notes`（字段为 `null`），不要写空字符串、不要写“无”、不要补一句“暂无备注”。也不要根据标题推测细节。
- **用户显式指定 → 按要求处理。** 包括给已有任务补写、追加、替换、清空。Agent 先用 `list` 定位唯一事件 ID，再调用 `update` 的 `changes.notes`；追加时把旧 notes 一并拼进新值；清空用 `notes: null`。匹配到多项或描述不清时先让用户选择。

示例（用户说：“把复现 qwen 人格的任务记到明天上午，配方是 L14 N8949 +1、L13 N7956 -1，结束时间暂定”）：

```json
{"action":"add","title":"复现 qwen3.5 4b 神经元转向","start":"2026-10-26T09:00:00+08:00","notes":"配方：L14 N8949 +1、L13 N7956 -1\n结束时间暂定"}
```

同一句话如果只说“明天上午复现那个 qwen 人格任务”，就只写标题和开始时间，不生成 `notes`。

## 修改与清空

```json
{"action":"update","id":"完整日程ID","changes":{"notes":"原步骤一\n原步骤二\n补充：先跑通加载再改 down_proj"}}
{"action":"update","id":"完整日程ID","changes":{"notes":null}}
```

`update` 是整字段替换，不是合并：追加要由 Agent 把旧值和新内容拼好再写入，避免静默丢内容。`notes: null` 清空备注但保留事件本身；删除事件用 `delete`。

## 保真与长度

- 数字、标识符、公式、链接逐字保留，不改写、不归纳成“见上文”、不四舍五入、不翻译变量名。
- 单条 `notes` 建议不超过 2000 字符；超长时保留关键条目（标识符、参数、公式、验收标准优先），并在末尾说明已截断。
- 多行用 `\n`；JSON 中的换行由调用方转义，脚本按原样存储。

## 显示位置

| 位置 | 是否显示备注 | 原因 |
| --- | --- | --- |
| 文本摘要（`summary.text`） | 显示，前缀 📝 | 手机上可读、可复制，适合长文本 |
| 每日卡片 PNG | 不显示 | 卡片是当天时间线的速览，塞入长备注会破坏排版 |
| `list` 返回值 | 显示 `notes` 字段 | 供 Agent 读取、拼接、判断是否已存在 |

因此细节写进 `notes`，不要写进 `title`：标题会被卡片折行展示，而且 `list --query` 的检索、冲突提示和摘要行都以标题为主。

## 隐私

`notes` 会进入本地 `events.json`、文本摘要和可能的推送记录，按个人数据处理：

- 不写密码、API key、token、卡号、验证码、身份证号等凭证；需要引用时写“见 1Password 条目 X”这类指代。
- 不把完整私密链接或带签名的 URL 贴进去；保留可检索的部分。
- 仓库、示例和截图中只使用虚构数据。

## 与其他规则的关系

- **时间**：`notes` 不影响开始/结束时间的解释；结束时间未知时仍然省略，不默认一小时。
- **冲突**：带 `notes` 的添加一样走冲突检测，冲突未保存时改时间或明确 `allow_conflict:true` 后重试。
- **定位**：修改或清空 `notes` 必须用 `list` 返回的完整 ID，不能用标题或 ID 前缀。
